# Bank statement import

On the Transactions screen, choose CSV / Excel, PDF, or Photo / Screenshot. Dragging a file onto the upload card also works. The statement automatically fills a read-only review table with dates, descriptions, amounts, income/expense types, categories and payment methods. Readable rows are selected by default. Check the table and choose Import. Edit is optional for corrections; Cancel edit restores the extracted value. Saved imports update the transactions list and financial summaries.

CSV and Excel support common bank headers, including Date / Transaction Date, Description / Narration / Particulars, separate Debit and Credit columns, or Amount with Type. Direction can also be filled from consistent running-balance changes and an opening balance, in ascending or descending date order. Amounts and balances must agree; ambiguous unsigned amounts are never guessed. Categories and payment methods are filled using the statement description when recognizable, with Other / Bank as defaults. Dates written as numbers in Excel use the workbook's calendar correctly. Text dates use Indian day/month/year order. A template is available on the upload card. Unreadable rows are visibly excluded and remain available for optional correction or a clearer re-upload.

PDF table extraction and photo/scanned-PDF text recognition run on the app server without an AI API key. Original PDF text coordinates preserve rows even when the file stores its text by column. Wrapped descriptions and amounts are joined, including digital transactions split across a page break. Column positions are retained on continuation pages without a header. Table geometry and OCR word positions preserve empty debit/credit cells; split monetary fragments are joined before reading amounts. OCR groups words on the same baseline across different text blocks, retries incomplete readings using sparse-text recognition, and also checks pages containing both digital text and images. No statement is sent to OpenAI or Gemini by this upload flow. A password is requested only when the uploaded PDF is protected. PDF passwords are used for extraction and are not stored. The original file is processed in memory; only the selected transaction fields are saved to your existing Supabase account. The OCR engine downloads public English language data on its first run and caches it in .cache/ocr.

PDF completeness checks compare detected dated rows with the chosen extraction. A remaining gap is reported with the affected page number and row counts. Pages with no recognized transactions are also identified for review. These checks can flag possible omissions; they cannot prove completeness when the source itself is unreadable. Unknown or incomplete transaction details are never invented.

Limits: 10 MB per file, 20 pages per PDF, 1,000 rows per import. Larger files are rejected; pages are not silently truncated. Supported image formats are PNG, JPG/JPEG and WebP. Clear scans work best. Unfamiliar or ambiguous layouts can require optional correction or a clearer export; automatic extraction cannot guarantee every bank layout or damaged/blurred document.

Repeated imports compare date, income/expense type, amount and normalized description against existing rows in your account. Matching counts are skipped while legitimate repeated rows within a statement are preserved. Duplicate checks must succeed before a single batch insert is attempted. Concurrent imports are serialized per account within one app process. Multiple deployment instances require a database-backed import identity/lock for the same concurrency guarantee. No new database migration is needed for this feature.

Validation: npm run test:imports checks CSV, Excel calendar systems and bank header aliases, balance-based direction inference across pages, numeric/direction validation, duplicate ownership and retries, concurrency, OCR column positions, wrapped/multiline rows and headers, actual text-PDF extraction and page limits. To include local photo, bank table and scanned/mixed-PDF checks, set RUN_OCR_TESTS=1 before running the same command. All 33 checks passed, including a real two-page synthetic bank PDF with column-first storage and a transaction split across pages, plus a single page containing digital and scanned transactions. These are synthetic fixtures; the user's actual Canara statement has not been supplied. Database insert/retry checks use a simulated account-scoped database.

Browser verification: an authenticated CSV upload displayed two populated read-only rows and correct income/expense totals with Import enabled immediately. Clicking Edit exposed only the chosen row's controls; Cancel edit restored the extracted description and enabled Import again. The test review was canceled without saving data. Targeted lint and the production build passed.

The app is available at http://localhost:3002/transactions. Refresh an old tab to load the updated upload card.
